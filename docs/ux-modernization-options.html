Where things stand

The bugs are fixed. The experience isn't.

  • Injured-starter warning
  • Fixed rookie salary table
  • Contracts layout on phones
  • Nav bar on phones, every page
  • Live Scoring tab removed
  • Repo matches production
  • Contracts
    A reference document, not a tool. 15,226 px on a phone, about 18 screens, listing every rostered player in the league. Members have to dig for their own cap space.
  • Look
    The site looks dated, and no stock skin fixes it. BlueMesh comes from MFL's 2017 skin set, and none of the alternatives are better.
  • Navigation
    Three rows on desktop. MFL's dropdown menu, MFL's nav bar and our tabs. Phones have been workable since PR #3; desktop is still cluttered, and MFL's two rows can't be removed.
  • Deploy
    Every release is pasted into five places. The header (fuadUtil) plus home page messages 3–6. The repo drifted for four seasons before PR #1.
  • Ritual
    A yearly code edit. year, beforeDraft, and the post-deadline franchise-player paste via the browser console.
  • Engine
    2012-era code underneath. jQuery 1.8, Underscore 1.4, Modernizr 2.6 and Handlebars 1.0 RC. Eight data requests run one after another (0.75 s; about 0.25 s in parallel), and no response is checked. That's how the injuries bug hid for years.
What decides the options

Code can live anywhere. It has to run inside MFL.

Our code running inside an MFL page→/2026/export?TYPE=rosters
Works

Same origin. The member's login comes along, so we know who's viewing and commissioner views work. MFL's terms exempt "calls from within league pages" from its rate limits.

A page hosted anywhere else→/2026/export?TYPE=rosters
Blocked

Exports send a fixed Access-Control-Allow-Origin: https://www44.myfantasyleague.com, and MFL's 2026 API terms forbid JavaScript access from other domains.

An MFL page→<script src> / stylesheet from GitHub Pages
Works

Loading code or styles from another domain is unrestricted, and the league page sends no Content-Security-Policy. The code is hosted elsewhere but runs in MFL.

  • League-wide hook
    fuadUtil sits in the shared header of every league page.One paste reaches every page, and CSS there outranks the skin, as PR #3 proved. So a league-wide look doesn't need a stock skin.
  • Custom CSS
    MFL supports league CSS by file or URL.Images & Other URLs Setup has a League CSS field. Restyling the site is within MFL's rules.
  • Navigation
    Our tabs are configurable; MFL's rows are not.Up to 10 tabs, renameable, with "Main" fixed. The nav bar's links and the dropdown menu can't be changed.
  • Phones
    Wide MFL modules already scroll sideways.MFL wraps home page modules in a scrolling box, so tables like Power Rankings are usable on phones as they are.
  • Hosting
    The repo is public.GitHub Pages hosting is free. It isn't enabled yet.

Your requirements

  1. Works well in a phone browser. We can't count on an app; MFL Modern fell short.
  2. No new navigation layer. Whatever we build lives inside a tab.
  3. The custom tabs stay as members know them.
  4. Within MFL's rules. No workarounds MFL would shut down.
  5. Stable year to year, with modest upkeep. Git, a build step and auto-deploy are acceptable.
What to build

Three pieces of work, each shippable on its own

None of them depends on how it's delivered. That's the separate decision below.

A · 2–3 days

Contracts, rebuilt around "My Team"

The league's own feature, and its worst phone experience. Goes from about 18 phone screens to one screen that answers the member's question.

  • Open with the viewer's franchise: cap space against $300, roster count against 23–30, who's expiring, and what cutting each player costs. MFL tells us who's logged in.
  • Cards on phones, a table on desktop, from the same data.
  • Contract state as badges (RFA, Expiring, Signed thru 2028) instead of "Years: 0".
  • The full league roster stays one tap away, collapsed by default.
  • Reference tables below: rookie salaries, franchise-tag salaries and the calculator.
B · ~2 days

Engine cleanup

Invisible to members, but it makes everything else cheaper and less fragile. Less work if done alongside A.

  • Replace the four 2012-era libraries with plain modern JavaScript.
  • Fetch the eight data requests in parallel and render as data arrives.
  • Check every response, and show a message on the page when something fails.
  • Derive year and the league ID from the page URL, so the season rollover is no longer a code edit.
  • Replace the post-deadline console ritual: a committed JSON file under Tier 2, or a generated paste under Tier 1.
C · 2–4 days

A league-wide look

The "it looks dated" complaint, addressed without a stock skin. Best done after A, so the new Contracts views set the visual language.

  • Our own stylesheet in the shared header: type, color, spacing, tables and module headers, on every league page.
  • Calmer desktop navigation: MFL's dropdown recedes, the nav bar reads as the main menu, and our tabs read as the league's own section. Nothing is hidden.
  • Phones first: larger tap targets and readable tables.

Risk This styles MFL's markup (#hsubmenu, .homepagemodule), which has been stable since 2017. If MFL changes it, parts of the look degrade but nothing breaks.

How it gets to the site

Six ways to deliver it, two worth doing

The remaining tiers. Tier 0 (settings, skin and apps) is done and dropped from the list.

TIER 1 · no setup

Keep pasting

As today: edit files in the repo, paste them into the header and messages 3–6.

For

  • Nothing new to set up or learn. Every change so far has shipped this way.

Against

  • Five paste targets per release, and the repo drifts whenever one is missed.
  • MFL's textareas are awkward for 400-line files.
  • The post-deadline ritual stays a console copy-and-paste.

Fits Small changes. It gets painful once A–C put far more code in those textareas. It's also Tier 2's fallback.

TIER 2 · ½ day setup

Load from GitHub Pages

fuadUtil shrinks to two tags and messages 3–6 to empty mount points. Everything else is served from bborchardt.github.io/fuadmflsite/ and goes live on git push.

<!-- the whole header paste, for good -->
<link rel="stylesheet" href="https://bborchardt.github.io/fuadmflsite/fuad.css">
<script src="https://bborchardt.github.io/fuadmflsite/fuad.js"></script>

For

  • Deploying is git push. You paste the header once, then only at season rollover, if at all.
  • The repo is production, so it can't drift.
  • The code still runs inside the MFL page: data access, logged-in identity, commissioner views and the rate-limit exemption all work as today.
  • The post-deadline snapshot becomes a small JSON file in the repo.
  • No build step required. Pages serves plain files. Add a bundler later only if the code needs one.
  • Same testing as now: serve the live page with new files swapped in before pushing.

Against

  • Custom content depends on GitHub Pages being up. If it's down, MFL's pages still work but our tabs are empty. A paste-able fallback build covers it.
  • Pages caches files for up to 10 minutes, so a push takes a few minutes to reach members.
  • If MFL ever adds a Content-Security-Policy, external scripts could be blocked. There is none today.

Recommended Half a day to move today's code over unchanged. Members see no difference until A–C ship.

TIER 3 · not recommended

A separate companion site, data baked at build time

A static site of its own, fed by a scheduled job that downloads MFL exports.

Fails requirements It's a second destination, a new navigation layer, and it can't tell who's viewing, so there's no "My Team". Its data is only as fresh as the last run, and the job is subject to MFL's per-IP rate limits.

TIER 4 · rejected

Companion site plus a proxy

Tier 3 with a server relaying MFL calls live.

Against MFL's terms It exists only to get around the same-origin rule, which MFL forbids in writing, and it funnels the whole league through one rate-limited IP.

TIER 5 · optional, later

A small public site for league history

Read-only and public: champions, records, bylaws, draft history. Nothing live, nothing that needs a login.

Verdict A shareable "front porch" with no data constraints, but a second destination and one more thing to maintain. Only after A–C. It could share Tier 2's GitHub Pages site.

TIER 6 · not recommended

Leave MFL

League Tycoon models salary caps, extensions, rookie scales and franchise tags natively.

Verdict The fixed rookie table makes the rules easier to model elsewhere. But the cap-penalty formula, RFA handling and franchise tags would depend on another platform's features, and a 25-year dynasty would need every owner to move. MFL's openness is what makes A–C possible.

Recommended sequence

Delivery first, then Contracts, then the look

Each step ships on its own and rolls back with git revert

  1. Set up Tier 2 (½ day). Move today's code to GitHub Pages unchanged and paste the two-tag header. Nothing changes for members.
  2. Build A, "My Team" Contracts (2–3 days), doing B's cleanup in the files it touches.
  3. Finish B (about 1 day): the remaining library removal, parallel loading and response checks.
  4. Design and ship C, the league-wide look (2–4 days), using A's visual language.
  5. Replace the post-deadline ritual with a committed snapshot. If Tier 2 isn't live by this season's deadline, do the paste the old way once more.
Design rules for A–C

What every screen should do

  • One primary navigation per screen size. MFL's nav bar is the main menu, and our tabs are the league's own section. Never add a third league menu.
  • Start from the member's question, not the data dump. "Can I afford this?" comes before "here is every contract".
  • Phones first. Cards under MFL's breakpoint, tables above it, 44 px tap targets.
  • Advanced things stay possible, one tap down: calculators, scales and commissioner tools.
  • Design the slow and broken states. Show the shell immediately, fill it as data arrives, and say so when a request fails.
So you're not rewriting this in 2029

Year-to-year stability

  • Derive the season and league from the URL; never hardcode a year.
  • Depend on as few MFL DOM hooks as possible: our own mount points, plus the selectors C needs to style.
  • Use documented export?TYPE= endpoints on the right host: league calls to www44, league-independent calls (players, injuries) to api.
  • Check every response; never treat HTTP 200 as success.
  • Keep a paste-able fallback build in the repo for a Pages outage.
  • Write the season rollover steps into the repo README.
