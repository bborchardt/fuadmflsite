The constraint that decides everything

Code can live anywhere. Data can't.

Every option below is really an answer to one question: where does the JavaScript run when it asks MFL for your rosters?

MFL's export API is same-origin only for browsers. Per MFL's own developer guidance, calling the API from a page outside myfantasyleague.com is blocked by normal browser security, and they will not add your domain to their cross-origin allowlist. Private-league data is gated further: authorization rides on the logged-in user's cookie, so a server has to log in as a real member to see it.

But loading a <script src> or a stylesheet from another domain has never been restricted — your current site already pulls jQuery and Handlebars from cdnjs. So the code and the data have completely different rules, and that gap is where the good options live.

Your JS running inside the MFL page→/2026/export?TYPE=rosters
Works

Same origin. The member's session cookie rides along automatically, so private-league data and commissioner-only views just work — and window.franchise_id tells you who's looking. No key, no secret, no server. This is what your current site does, and it's the single best thing about it.

Your JS on a site you host→/2026/export?TYPE=rosters
Blocked

The browser refuses the cross-origin read and MFL declines to allowlist third-party domains. No amount of front-end work gets around this; it needs a server in the middle.

A build job or serverless function→/2026/export?TYPE=rosters
Works, with strings

Server-side calls are fine and explicitly supported — but you need the league API key, a stored MFL login for private data, a registered User-Agent, and roughly one request per second with aggressive caching. That's a credential to rotate and a rate limit to respect, forever.

Where it actually hurts

What I found in the repo

Five files, about 1,150 lines, pasted by hand into MFL's home page message boxes. The logic is sound — the packaging is what's aged.

  • Drift
    Git no longer matches production. The last commit is "Updates for 2022" and fuadUtil.html still says var year = "2022", with franchise-player salaries frozen at 2021 names. The live site is on 2026. The real source of truth is a set of textareas in MFL admin, which means the repo can't be trusted as a starting point until it's reconciled.
  • Mobile
    The layout is a fixed-width table from 2001. <table id="homepagecolumns"> with width="65%" / width="35%", cellspacing and align="center". A seven-column contract table cannot reflow on a phone. This is the single biggest reason the site feels bad on mobile — and it's yours, not MFL's.
  • Setting
    MFL may already be trying to help, and the markup is fighting it. When Desktop View On Mobile is set to No, MFL injects a viewport meta tag and a responsive stylesheet into the skin. Worth confirming that's on — a responsive skin wrapped around a rigid table still reads as broken.
  • Fragile
    One line reaches into MFL's own markup. fuadCommish.hbs:134 does $("#tabcontent0").find("#homepagecolumn1").prepend(html). That depends on MFL's internal DOM structure and IDs. It is the most likely thing in the codebase to break silently on an MFL update, and the hardest to notice when it does.
  • Stack
    Every dependency is 13+ years old, and one is load-bearing. jQuery 1.8.0, Underscore 1.4.2, Modernizr 2.6.2, Handlebars 1.0.rc.1 — a release candidate. The checkbox handling uses .attr("checked"), whose meaning changed in jQuery 1.9, so the version pin isn't a preference, it's a dependency. Modernizr is loaded to feature-detect localStorage, which has been universal for over a decade.
  • Speed
    Eight requests in a chain, each waiting on the last. Players, franchises, salary adjustments, rosters, transactions, weekly results, free agents, injuries — loaded strictly in sequence as XML, when six of the eight are independent and could run at once. The full NFL player database is fetched and cached into localStorage; on a phone that's a lot of parsing before anything renders. JSON=1 is available and would drop the XML parsing entirely.
  • Ritual
    Three hand-edits a year, one of them via the console. year, beforeDraft and beforeTradeDeadline are hardcoded, and after the trade deadline a commissioner clicks a button that console.logs a block of JavaScript to copy back into the source. Year and league ID are both already sitting in the page URL and could be derived. This is exactly the "avoid rewrites, stay stable year to year" problem you named.
  • Keep
    The architecture is genuinely right, though. Running same-origin inside MFL gets you cookie auth, private-league access, per-member identity, zero hosting, zero secrets — and it's purely additive, so MFL keeps owning lineups, trades, waivers and scoring. Whatever you build next, don't give this up cheaply.
The options — ordered by what you'd be committing to

Seven routes, from an afternoon to a migration

The tiers aren't a ranking. They're escalating commitment: each one costs more to build and more to keep alive than the one above it. Tiers 0 and 2 are the ones I'd actually do.

TIER 0 · an afternoon

Settings, skin, and send everyone to an app

Write no code. Confirm Desktop View On Mobile is off, pick a modern skin from MFL's 40+ (or a free responsive template from MFL.football / MFLaddons), tidy the home page module and tab arrangement, and tell the league to use MFL Modern, MFL Mobile or MFL Platinum on their phones.

For

  • Rosters, lineups and live scores — the job you said matters most — are 100% MFL-native. Third-party apps already do them well on mobile, and someone else maintains them.
  • MFL Modern is free for one team in one league and logs in with existing MFL credentials, so there's nothing for you to administer.
  • Zero maintenance, zero risk, survives every MFL change. Nothing to rewrite next August.
  • Establishes the visual baseline before you spend effort — you may find half the complaint disappears.

Against

  • Does nothing for the contract and cap layer, which is your league's actual differentiator and the whole reason this repo exists.
  • You don't control the design; a skin repaints, it doesn't reorganize what's on the page.
  • Third-party apps can be abandoned, go paid, or lag MFL's feature changes. Three exist today; that's also a hint none is definitive.
  • Apps generally won't render your custom home page modules, so members on mobile may not see the contract views at all.

Verdict Do this first regardless of what else you choose. It's the highest return per hour on the page, and it tells you how much of the remaining problem is really yours to solve.

TIER 1 · a weekend

Modernize in place, keep pasting

Same deployment model — files pasted into home page messages — but rewrite them. Drop all four libraries for vanilla ES2020 and template literals, replace the table layout with CSS grid plus a card view under a breakpoint, switch to JSON=1, run the independent fetches with Promise.all, and derive year and league ID from the URL.

For

  • Smallest possible change of habit — nothing new to learn, nothing new to host.
  • Kills the two worst problems outright: the rigid table and the hardcoded year.
  • Zero dependencies means nothing left to bit-rot. A file with no CDN links is the most stable artifact you can put in an MFL textarea.
  • Keeps every advantage of running same-origin.

Against

  • Still deploys by copy-paste into a textarea, so git will drift from production again — that's how you got here.
  • No local preview, no tests, no way to try a change without editing the live league site.
  • Under-uses the budget you said you'd accept. You're willing to run a build; this option declines it.

Verdict A solid answer if you later decide you want zero infrastructure. Otherwise it's Tier 2 minus the part that fixes the drift.

TIER 2 · a week, then git push

A three-line loader in MFL, the real app on GitHub Pages

One home page message holds a mount point and two tags pointing at bborchardt.github.io/fuadmflsite/. Everything else lives in the repo, builds with Vite or esbuild, and deploys on push via GitHub Actions. The app renders inside the MFL page, so every data call is still same-origin.

For

  • Modern tooling and auto-deploy — exactly the budget you set — with none of the data problems, because the code still executes on MFL's origin.
  • Deploying is git push. You stop visiting MFL admin, and the repo becomes the source of truth again.
  • No API key, no stored credentials, no proxy, no CORS workaround, no rate-limit accounting. Private league and commissioner views keep working by cookie.
  • One URL for the league. Members never learn a second site exists.
  • Point the loader at localhost in your own browser to preview changes against real league data before shipping.
  • Nothing here is a backdoor — external <script src> is what the site already does, and MFL gives leagues disk space for custom code.

Against

  • The MFL page now depends on GitHub Pages being reachable. Mitigate by keeping a built copy in MFL's own league file space as a fallback source.
  • You still inherit MFL's page chrome, skin CSS and tab structure. You're designing a room inside someone else's house.
  • If MFL ever adds a Content-Security-Policy that blocks third-party scripts, the loader breaks — low odds, and the MFL-hosted fallback copy covers it.
  • Someone still pastes the loader once per season when the league rolls over.
  • Slightly more moving parts than Tier 1 for a commissioner who inherits this in five years.

Verdict The recommendation. It is the only option that gets you a modern build pipeline without giving up cookie auth, per-member identity, or the single-destination experience.

TIER 3 · two weeks + a secret to rotate

A companion site with data baked at build time

A GitHub Actions cron fetches the MFL exports server-side, commits the JSON, and a static site (Astro, SvelteKit, Next export) renders a fully custom dashboard. Optionally iframed back into an MFL tab.

For

  • Total design freedom — real components, dark mode, charts, a proper mobile navigation, none of MFL's chrome.
  • Fast, because the data is pre-computed static JSON. Nothing is calculated in the member's browser.
  • Testable and previewable like any normal app, with PR previews.
  • Room to blend in outside data — dynasty values, ADP, historical charts — that MFL doesn't carry.

Against

  • Data is only as fresh as the last cron run — which directly undercuts rosters, lineups and live scores, the job you named as most common.
  • Private-league data needs a stored MFL login or API key in GitHub secrets: a real credential to guard and rotate.
  • The site can't tell who's viewing, so there's no "your team" view and no commissioner-only tools without building auth yourself.
  • Two destinations, or an iframe that behaves badly on phones.
  • Every MFL auth or export change is now your emergency. This is the option most likely to force a rewrite.

Verdict Genuinely good for read-only, slow-moving content. A poor fit for the jobs you actually prioritized.

TIER 4 · ongoing ownership

Companion site plus a serverless proxy

Tier 3, but a Cloudflare Worker or Vercel function proxies MFL calls live at request time, holding the API key and a logged-in session cookie.

For

  • Live data and full design freedom at the same time — the only option that gets both.
  • A place to cache, precompute and shape data into an API that fits your league's rules exactly.
  • Could eventually serve a real mobile app or notifications.

Against

  • You now own credentials, a proxy, cache invalidation, and rate-limit compliance for your entire league's traffic funnelled through one identity.
  • MFL says plainly they won't allowlist third-party domains for browser access. Proxying around that is legal but leans on the letter rather than the spirit — the thing you asked to avoid.
  • Most to maintain, most to break, highest chance of a forced rewrite when MFL changes login or session handling.
  • Directly contradicts "stable year to year."

Verdict Not recommended. It buys design freedom at exactly the price you said you didn't want to pay.

TIER 5 · later, if you want one

Hybrid — Tier 2 for the league, a small public site for the front porch

The in-MFL app owns everything that needs authentication: cap sheets, contracts, commissioner tools, live views. A separate static site owns the read-only, no-auth material — league history, bylaws, records, hall of fame, championship charts.

For

  • Each half uses the mechanism it's actually suited to, with no compromises in either.
  • The public site can be genuinely beautiful and shareable without touching a credential.
  • League history is exactly the content that doesn't need to be fresh — the Tier 3 staleness problem evaporates.

Against

  • Two build targets and two deploys, even in one monorepo.
  • More concepts for a future commissioner to hold in their head.
  • Easy to start and never finish, leaving a half-built second site.

Verdict A good year-two move on top of Tier 2, not a starting point.

TIER 6 · due diligence

Leave MFL for a platform with native contracts

League Tycoon handles salary caps, multi-year extensions, rookie scales and franchise tags natively at about $12 per team per year, and imports MFL salary and contract data plus past seasons. Fantrax has native salary cap and a cleaner web UI, but a weak app.

For

  • The contract logic you hand-maintain becomes someone else's product feature. The annual JavaScript ritual ends permanently.
  • Modern, mobile-first UI is their problem, not yours — and it's the whole basis of their competition.
  • Import claims to carry salaries, contract years and up to 20 prior seasons across, so the history isn't necessarily lost.

Against

  • Your rules are idiosyncratic. Anything the platform doesn't model natively — your specific cap-penalty formula, your rookie salary curve, your RFA handling — becomes worse than today, because you lose the escape hatch of writing your own code.
  • MFL's openness is precisely why this repo works at all. A polished closed platform trades that away.
  • Migration risk mid-dynasty, and buy-in needed from every owner.
  • Betting a 25-year league on a newer company is a bigger bet than staying.

Verdict Worth an hour of looking so you know what you're choosing against. Not a recommendation — your custom rules are the reason to stay.

The sequence

  1. Check the mobile setting and the skin first. If Desktop View On Mobile is still on, or the skin is a 2012 pick, you're solving a problem MFL already solved. Cheap, and it changes what "outdated" means before you write anything.
  2. Reconcile the repo with production. Pull the current text out of each home page message and commit it. Right now nobody knows what's actually running — that has to be true before any rebuild.
  3. Build the loader. One home page message with a mount div and two tags. Everything else in the repo, built and deployed by Actions. Deploying stops meaning "log into MFL."
  4. Rewrite the contract views mobile-first — cards under a breakpoint, table above — and derive year and league ID from the URL so the season rollover stops being a code edit.
  5. Point the league at MFL Modern for phone lineup-setting, and stop trying to out-build it.
Independent of which option you pick

What to actually design

The technology question is separate from the information-architecture one. These apply either way.

Lead with one "My Team" view

Today the contract tab opens with every rostered player in the league, grouped by contract year. That's a reference document, not a landing page. The questions members actually arrive with are: how much cap space do I have, am I legal on roster count, who's expiring, and what does it cost me to cut this guy. Put those five numbers at the top, for the logged-in franchise — you already know who they are.

Cards on phones, table on desktop, one data source

A seven-column contract table is the right tool at 1200px and useless at 390px. Render the same player objects as stacked cards below a breakpoint. This single change does more for perceived quality than any restyling.

Make contract state legible, not numeric

"Years: 0" currently means restricted free agent, which you have to know to read. A badge — RFA, Expiring, Signed thru 2028 — carries it at a glance. Encode state in form and color, not just digits.

Advanced things stay possible, but behind a door

The cap penalty calculator, the rookie salary scale, the franchise-tag tables and the commissioner forms are all genuinely useful and none belong on first paint. Put them behind a Tools section. Progressive disclosure is how you get "common functions easy, advanced functions possible" without two separate sites.

Design the empty and slow states

Eight chained requests means members currently stare at a blank column. Render the shell immediately, fill sections as data lands, and say something when a fetch fails instead of silently rendering nothing.

So you're not rewriting this in 2029

The year-to-year stability checklist

Whatever you build, these are the rules that decide whether it survives unattended. Most of the current pain traces to breaking three of them.

  • Derive year and league ID from document.location. Never hardcode a season.
  • Depend on exactly one MFL DOM hook — your own mount point. Delete the #tabcontent0 / #homepagecolumn1 reach-in; it will break and it will break quietly.
  • Use only documented export?TYPE= endpoints. Never parse MFL's rendered HTML.
  • Compute the post-deadline franchise and rookie baselines rather than pasting generated code. If a snapshot is genuinely needed, store it in MFL, not in the source file.
  • Pin exact dependency versions, and vendor them into the build so a CDN outage isn't a league outage.
  • Keep a built copy of the bundle in MFL's league file space as a fallback if the primary host is external.
  • Write down the season rollover procedure in the repo. There isn't a README today, and the ritual lives only in your head.
  • Prefer boring, dependency-light code. This site is edited a few days a year by one person; cleverness costs more than it returns.

What to verify before committing

All myfantasyleague.com domains were blocked by this session's network policy, so I could not open your live site, the API docs, or the MFL forums directly. The repo analysis is first-hand from the code. The MFL platform specifics below come from search results and third-party sources, and three claims are worth confirming yourself before you build on them: (1) that MFL still declines cross-origin browser access and won't allowlist domains — check Help → Developer's API while logged in; (2) that league file space accepts a JS/CSS upload you can reference by URL; (3) that your league's Desktop View On Mobile setting is currently off.
