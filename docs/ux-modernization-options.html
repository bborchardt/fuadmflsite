The site today

It works. The experience is the problem.

MFL's BlueMesh skin, with three navigation rows: MFL's dropdown menu, MFL's nav bar, and seven custom tabs (Main, Standings, Transactions, Contracts, Calendar, Commish, Links). On phones the dropdown menu and the custom tabs each collapse to a "+" bar, and MFL's nav bar shows as a swipeable row on every league page.

The league's own features are custom code: a rules-violation check on Main, plus the Contracts, Commish and Links tabs. That code is pasted into the shared page header (fuadUtil) and home page messages 3–6, and the repo matches what's deployed.

  • Look
    The site looks dated, and no stock skin fixes it.BlueMesh dates from MFL's 2017 skin set.
  • Contracts
    A reference document, not a tool.15,226 px on a phone, about 18 screens, listing every rostered player in the league.
  • Navigation
    Three rows on desktop.Phones show one swipeable nav row; desktop shows all three, and MFL's two can't be removed.
  • Deploy
    Every release is pasted into five places.The repo goes out of date whenever a paste is missed.
  • Chores
    Commissioner chores are manual.Contract years on adds, cap penalties on drops, watching for over-cap moves, and a post-deadline franchise-salary paste via the browser console.
  • Engine
    2012-era code underneath.jQuery 1.8, Underscore 1.4, Modernizr 2.6 and Handlebars 1.0 RC. Eight data requests run one after another, and no response is checked.
What MFL allows

Code can live anywhere. It has to run inside MFL.

Our code running inside an MFL page→/2026/export?TYPE=rosters
Works

Same origin. The member's login comes along, and MFL exempts "calls from within league pages" from its rate limits.

A page hosted anywhere else→/2026/export?TYPE=rosters
Blocked

MFL's exports only allow its own origin, and its API terms forbid JavaScript access from other domains.

An MFL page→script and stylesheet from GitHub Pages
Works

Loading code from another domain is unrestricted, and the league page sends no Content-Security-Policy.

A once-a-day job on GitHub→MFL API, logged in as commissioner
Works, with a keepalive

Server-side calls are supported and far below any rate limit. GitHub disables scheduled jobs after 60 days without repo activity, so the job re-enables itself on every run.

  • Header
    fuadUtil sits in the shared header of every league page.One header reaches every page, and CSS there outranks the skin.
  • Seasons
    MFL keeps each past season's site and copies the header forward at renewal.Each season's header can pin its own code version.
  • Writes
    The commissioner's login can write.Salary adjustments, contract years and salaries, and add/drop moves on a team's behalf, all through MFL's documented import API.
  • Bids
    Bid messages are on the logged-in Prior FA Bids page, not in the API.They can be read from that page, which isn't a documented API and may change.
  • Salaries
    Rosters by week keep membership, but salaries always show current values.A cut player reads $1, so franchise salaries must be snapshotted at the deadline, not recomputed later.
  • Schedule
    MFL's NFL schedule gives every kickoff time.Week 1 and the week 12 trade deadline are computed, never entered.

Your requirements

  1. Works well in a phone browser.
  2. No new navigation layer. The custom tabs stay as members know them.
  3. Within MFL's rules.
  4. Stable year to year, with as few chores to remember as possible.
Decisions

How it will work

DELIVERY

Versioned code on GitHub Pages

The MFL header holds a stylesheet link and a script tag pointing at a version. Messages 4–6 hold one-line mount points.

<link rel="stylesheet" href="https://bborchardt.github.io/fuadmflsite/v1/fuad.css">
<script type="module" src="https://bborchardt.github.io/fuadmflsite/v1/fuad.js"></script>
  • Versions live in site/v1/, site/v2/… and are published on every push. New versions start dark; activating or reverting is a one-line header edit.
  • Archives pin themselves: each season's site keeps the header it ended with.
  • Changing an active version in place is the maintainer's call: fine for low-risk tweaks, undone with git revert.
  • Preview: a setting stored only in your browser loads a dark version or your laptop's copy on the live site, limited to localhost and this repo's versions.
  • Resilience: a "league tools unavailable" message if Pages is down, and a paste-able fallback build in the repo.
FRANCHISE

Franchise salaries switch automatically

Each phase is labeled on the page. The commissioner button stays as a manual backup.

  • Before the week 1 kickoff, a stand-in for the offline rookie draft: last season's snapshot.
  • Week 1 to the trade deadline (first kickoff of week 12): a live projection.
  • After the deadline: this season's snapshot.
AUTOMATION

A daily GitHub job

Runs early each morning (Central time), logged in as commissioner with the password in GitHub's encrypted secrets.

  • v1: takes the franchise snapshot after the deadline and publishes it.
  • Chore log on its own chore-log branch: an entry when something happens, plus a monthly heartbeat.
  • Keepalive: re-enables itself through GitHub's API on every run.
  • No message board posts for now; they can be turned on after seeing the log in action.
LOGIC

League logic written once

Cap math, the penalty formula, the rookie table, franchise rules and the season phases live in plain JavaScript modules imported by both the page and the job, so the two can't disagree.

Open questions for the chores version

  1. Contract years on first-come-first-served adds: read free-text message board posts, or add a structured "Set contract length" control for members?
  2. Over-cap moves: flag with a one-click reverse, or flag only?
  3. A saved copy of the Prior FA Bids page is needed to build its parser.

Ruled out

  • Companion site
    A second destination is a new navigation layer, and it can't tell who's viewing.
  • Proxy
    Against MFL's API terms.
  • Leave MFL
    Would give up the custom rules MFL's openness allows.
  • History site
    Optional, and only after A and C.
Design rules

What every screen should do

  • One primary navigation per screen size. MFL's nav bar is the main menu, and our tabs are the league's own section. Never add a third league menu.
  • Start from the member's question, not the data dump.
  • Phones first. Cards under MFL's breakpoint, tables above it, 44 px tap targets.
  • Advanced things one tap down: calculators, scales and commissioner tools.
  • Design the slow and broken states. Show the shell immediately, fill it as data arrives, and say so when a request fails.
  • Automation is visible. Every automated change is logged, and anything risky is flagged for a person rather than done.
