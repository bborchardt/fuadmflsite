The constraint that decides everything

Code can live anywhere. Data can't.

Every option below is really an answer to one question: where does the JavaScript run when it asks MFL for your rosters?

MFL's export API is same-origin only for browsers. This is no longer an inference — every export response carries a static allow-origin header naming MFL's own host, and it is never reflected back. Sending Origin: https://bborchardt.github.io, Origin: https://evil.example.com, or no origin at all returns the identical value:

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://www44.myfantasyleague.com

And MFL's 2026 API terms list this under forbidden uses, in their words: "Accessing the API via Javascript from web pages outside the myfantasyleague.com domain. Normal browser security will prevent this from working and we will not put your domain in our cross-domain file to allow it." Revised: the first draft treated this as a technical obstacle. It is also a terms-of-service line — which changes the verdict on Tier 4.

The rate limit points the same way. MFL throttles per IP address, and says so explicitly: "if your client is spread across many users, it won't be affected… mobile apps and calls from within league pages should not [be] affected." In-page code spreads across twelve members' own connections and is named as exempt. A cron job or proxy funnels the whole league through one address — exactly the shape the limits target. That is an argument for Tier 2 and against Tiers 3–4, from MFL directly.

But loading a <script src> or a stylesheet from another domain has never been restricted — your current site already pulls jQuery and Handlebars from cdnjs. So the code and the data have completely different rules, and that gap is where the good options live.

Your JS running inside the MFL page→/2026/export?TYPE=rosters
Works

Same origin. The member's session cookie rides along automatically, so private-league data and commissioner-only views just work — and window.franchise_id tells you who's looking. No key, no secret, no server. This is what your current site does, and it's the single best thing about it.

Your JS on a site you host→/2026/export?TYPE=rosters
Blocked

Confirmed by direct test — the allow-origin header is hardcoded to MFL's own host. No amount of front-end work gets around this; it needs a server in the middle, and MFL's terms forbid building one for this purpose.

A build job or serverless function→/2026/export?TYPE=rosters
Works, with strings

Server-side calls are fine and explicitly supported. Revised: no API key is needed to read this league — all seven league endpoints answer unauthenticated. But you inherit the per-IP rate limit that in-page code is exempt from, plus a registered User-Agent, ~1 request/sec, and a stored MFL login if the league ever goes private.

Where it actually hurts

What I found in the repo, re-checked against production

Five files, about 1,150 lines, pasted by hand into MFL's home page message boxes. The logic is sound — the packaging is what's aged. Everything below was re-checked against the live 2026 site.

  • Drift
    Reconciled — and much smaller than it looked. Revised. The first draft said nobody knew what was actually running. Now we do: all five modules were pulled off the live page and diffed. Ignoring whitespace, the entire drift is year "2022"→"2026", beforeDraft true→false, the 58-line franchise/rookie settings block refreshed to 2025 names, and one stray production-only console.log in fuadAjax. fuadContract, fuadCommish and fuadLinks are byte-identical. The drift sits entirely inside the block the code itself labels "update these after upgrading site" — the annual ritual, exactly where you'd expect it. Reconciliation is a mechanical 60-line commit, not archaeology. It also means the paste workflow is faithful and recoverable, which matters later.
  • Mobile
    The outer layout already stacks. Our tables are what overflow. Revised, and this narrows the job. The first draft blamed <table id="homepagecolumns"> and its width="65%"/35%. But MFL's own responsive.css already forces #homepagecolumn1, #homepagecolumn2 { width:100%!important } below 62.5em — the two-column shell does collapse correctly on a phone. What doesn't reflow is the seven-column contract table we generate (Player, Position, Salary, Contract Year, Cap Penalty, Net Cap Space, Franchise), overflowing sideways inside its now-full-width column. Better still, MFL's stylesheet already ships the table→card idiom — .report th{display:none} .report td{display:block} — just scoped to one page. Our tables already carry MFL's class="homepagemodule report", so reusing that pattern is native rather than an override.
  • Setting
    Already correct. Nothing to change — and the easy win is already spent. Revised. The live page serves <meta name="viewport" content="initial-scale=1.0, width=device-width"> and loads skins17/BlueMesh/responsive.css. Desktop View On Mobile is off already and the skin is a responsive one. That retires the first draft's step-one recommendation as a no-op — welcome news, but it also means the remaining mobile problem is entirely ours. There is no setting left to flip.
  • Fragile
    One line reaches into MFL's own markup — around an MFL bug. fuadCommish.hbs:134 does $("#tabcontent0").find("#homepagecolumn1").prepend(html). New context: the live page contains eight elements carrying id="homepagecolumn1", one per tab — invalid HTML that MFL ships anyway, and the whole reason this selector has to be scoped through #tabcontent0. So the line is working around a markup bug on MFL's side, which makes it likelier than average to break the day they clean it up. Replace it with our own mount point.
  • Stack
    Every dependency is 13+ years old — and all four are safe to delete. jQuery 1.8.0, Underscore 1.4.2, Modernizr 2.6.2, Handlebars 1.0.rc.1 — a release candidate. The checkbox handling uses .attr("checked"), whose meaning changed in jQuery 1.9, so the version pin isn't a preference, it's a dependency. Modernizr is loaded to feature-detect localStorage, universal for over a decade. New: MFL's own mfl_common.js contains no jQuery and no $ usage, and the page loads jQuery exactly once — from our tag. Nothing on MFL's side depends on any of these, so dropping all four is safe from the platform's point of view; the jQuery.noConflict() call is defensive, not load-bearing.
  • Speed
    Eight requests in a chain — measured at 2.50 s, against 0.58 s in parallel. Players, franchises, salary adjustments, rosters, transactions, weekly results, free agents, injuries — strictly sequential XML. Timed end-to-end from a datacenter on a warm connection: 2.50 s sequential vs 0.58 s for the same eight at once, a 4.3× gap that widens sharply on phone networks. The ordering is a processing dependency, not a fetching one — only injuries truly needs a prior response (week, from weeklyResults). Fetch all eight together, then process in order. Revised on JSON=1: it works everywhere but is not a payload win — players 190 KB→183 KB, freeAgents 51 KB→48 KB, about 5%. Switch to delete the XML DOM-walking code, not to save bytes.
  • Ritual
    Three hand-edits a year, one of them via the console. year, beforeDraft and beforeTradeDeadline are hardcoded, and after the trade deadline a commissioner clicks a button that console.logs a block of JavaScript to copy back into the source. Year and league ID are both already sitting in the page URL and could be derived. This is exactly the "avoid rewrites, stay stable year to year" problem you named.
  • Keep
    The architecture is genuinely right, though. Running same-origin inside MFL gets you cookie auth, private-league access, per-member identity, zero hosting, zero secrets — and now demonstrably a rate-limit exemption MFL grants in writing to "calls from within league pages." It's purely additive, so MFL keeps owning lineups, trades, waivers and scoring. Whatever you build next, don't give this up cheaply.
Found by actually calling the API

Injured-player detection has never worked

This is independent of every option below, it has been broken the whole time, and no amount of code reading would have caught it. It deserves a one-line fix regardless of what you decide.

fuadUtil.html:164 builds the injuries URL off the league host:

injuriesDataUrl: baseUrl + "export?TYPE=injuries&L=" + leagueId + "&W="

which resolves to www44.myfantasyleague.com/2026/export?TYPE=injuries&L=48571&W=1. MFL answers that with an error document — at every week tried:

<error>Invalid request. This API request must go to api.myfantasyleague.com</error>

The reason is in MFL's own docs: "if the request does not take a league parameter (L=), it must be sent to the host api." Injuries is global NFL data, not league data — it takes no L. Drop it, switch hosts, and 36 KB of real <injury> nodes come back:

https://api.myfantasyleague.com/2026/export?TYPE=injuries&W=1   →  200, 36 KB

What it costs you. loadInjuriesData runs getElementsByTagName("injury") over an error document, finds nothing, and silently sets no flags. player.injured is therefore never true — so this check in fuadCommish.hbs:121 has never once fired:

warnings.push(franchise.teamName + " started injured/suspended player " + player.fullName + …)

A league-rules warning shown on the Main tab to everyone has been dead for years, with no error and no empty state to hint at it. It fails quietly because the loader treats any HTTP 200 as success.

The fix is one line. The lesson is bigger: eight unchecked $.get calls means any of them can fail exactly this quietly. Whichever tier you pick, the loader needs to check that a response is the shape it expected — and say so on the page when it isn't.

Tested logged-out. The error is host-routing, not authentication, so it will behave identically for a signed-in member — but it costs nothing to confirm in the browser console.

The options — ordered by what you'd be committing to

Seven routes, from an afternoon to a migration

The tiers aren't a ranking. They're escalating commitment: each one costs more to build and more to keep alive than the one above it. Tiers 0 and 2 are the ones I'd actually do.

TIER 0 · ~2 hours, revised down

Settings, skin, and send everyone to an app

Write no code. Confirm Desktop View On Mobile is off, pick a modern skin from MFL's 40+ (or a free responsive template from MFL.football / MFLaddons), tidy the home page module and tab arrangement, and tell the league to use MFL Modern, MFL Mobile or MFL Platinum on their phones.

For

  • Rosters, lineups and live scores — the job you said matters most — are 100% MFL-native. Third-party apps already do them well on mobile, and someone else maintains them.
  • MFL Modern is free for one team in one league and logs in with existing MFL credentials, so there's nothing for you to administer.
  • Zero maintenance, zero risk, survives every MFL change. Nothing to rewrite next August.
  • All three apps are still listed and live — MFL Modern (newest), MFL Mobile, MFL Platinum — so the recommendation still stands.

Against

  • Does nothing for the contract and cap layer, which is your league's actual differentiator and the whole reason this repo exists.
  • You don't control the design; a skin repaints, it doesn't reorganize what's on the page.
  • Third-party apps can be abandoned, go paid, or lag MFL's feature changes. Three exist today; that's also a hint none is definitive.
  • Apps generally won't render your custom home page modules, so members on mobile may not see the contract views at all.

Verdict — revised Still worth doing, but it is no longer the free win it looked like. The mobile setting and responsive skin are already correct, so this tier shrinks to "pick a nicer skin, tidy the tabs, point members at an app." The easy half has already been collected — which means the remaining mobile problem is entirely yours.

TIER 1 · a weekend

Modernize in place, keep pasting

Same deployment model — files pasted into home page messages — but rewrite them. Drop all four libraries for vanilla ES2020 and template literals, replace the table layout with CSS grid plus a card view under a breakpoint, switch to JSON=1, run the independent fetches with Promise.all, and derive year and league ID from the URL.

For

  • Smallest possible change of habit — nothing new to learn, nothing new to host.
  • Kills the two worst problems outright: the rigid table and the hardcoded year.
  • Zero dependencies means nothing left to bit-rot. A file with no CDN links is the most stable artifact you can put in an MFL textarea.
  • Keeps every advantage of running same-origin.

Against

  • Still deploys by copy-paste into a textarea, so git will drift from production again — that's how you got here.
  • No local preview, no tests, no way to try a change without editing the live league site.
  • Under-uses the budget you said you'd accept. You're willing to run a build; this option declines it.

Verdict — revised upward A more respectable fallback than the first draft allowed. Now that the drift turns out to be 60 contained lines rather than scattered rot, the paste workflow looks faithful rather than lossy — and it doubles as Tier 2's safety net.

TIER 2 · a week, then git push

A three-line loader in MFL, the real app on GitHub Pages

One home page message holds a mount point and two tags pointing at bborchardt.github.io/fuadmflsite/. Everything else lives in the repo, builds with Vite or esbuild, and deploys on push via GitHub Actions. The app renders inside the MFL page, so every data call is still same-origin.

For

  • Modern tooling and auto-deploy — exactly the budget you set — with none of the data problems, because the code still executes on MFL's origin.
  • Deploying is git push. You stop visiting MFL admin, and the repo becomes the source of truth again.
  • No API key, no stored credentials, no proxy, no CORS workaround — and no rate-limit exposure, since MFL exempts "calls from within league pages" in writing. Private league and commissioner views keep working by cookie.
  • One URL for the league. Members never learn a second site exists.
  • Point the loader at localhost in your own browser to preview changes against real league data before shipping.
  • Nothing here is a backdoor — external <script src> is what the site already does, and MFL gives leagues disk space for custom code.

Against

  • The MFL page now depends on GitHub Pages being reachable. Fallback corrected: the first draft proposed parking a built copy in MFL's league file space. Only partly supported — league files do serve same-origin from fflnetdynamic2026/48571_*, but the documented upload UI accepts CSS only and directory listing is 403, so treat JS hosting there as unconfirmed. The reliable fallback is the mechanism already in use: paste the built bundle into a home page module. That is Tier 1 — which makes Tier 1 the genuine safety net for Tier 2, since the two share all their code.
  • You still inherit MFL's page chrome, skin CSS and tab structure. You're designing a room inside someone else's house.
  • Re-assessed: the first draft worried about a future MFL Content-Security-Policy blocking third-party scripts. The league page sends no CSP header at all today (nor X-Frame-Options), so this is hypothetical rather than a live constraint.
  • Someone still pastes the loader once per season when the league rolls over.
  • Slightly more moving parts than Tier 1 for a commissioner who inherits this in five years.

Verdict Still the recommendation, and better supported than in the first draft. The only option that gets a modern build pipeline without giving up cookie auth, per-member identity, the rate-limit exemption, or the single-destination experience.

TIER 3 · two weeks + a secret to rotate

A companion site with data baked at build time

A GitHub Actions cron fetches the MFL exports server-side, commits the JSON, and a static site (Astro, SvelteKit, Next export) renders a fully custom dashboard. Optionally iframed back into an MFL tab.

For

  • Total design freedom — real components, dark mode, charts, a proper mobile navigation, none of MFL's chrome.
  • Fast, because the data is pre-computed static JSON. Nothing is calculated in the member's browser.
  • Testable and previewable like any normal app, with PR previews.
  • Room to blend in outside data — dynasty values, ADP, historical charts — that MFL doesn't carry.

Against

  • Data is only as fresh as the last cron run — which directly undercuts rosters, lineups and live scores, the job you named as most common.
  • Revised: no API key is needed to read this league — all seven league endpoints answer unauthenticated, so the credential burden is lighter than first stated. But the per-IP rate limit now applies where in-page code was exempt, and a stored MFL login returns the moment the league goes private.
  • The site can't tell who's viewing, so there's no "your team" view and no commissioner-only tools without building auth yourself.
  • Two destinations, or an iframe. (The iframe would at least work — MFL sends no X-Frame-Options — but it still behaves badly on phones.)
  • Every MFL auth or export change is now your emergency. This is the option most likely to force a rewrite.

Verdict Genuinely good for read-only, slow-moving content. A poor fit for the jobs you actually prioritized.

TIER 4 · ongoing ownership

Companion site plus a serverless proxy

Tier 3, but a Cloudflare Worker or Vercel function proxies MFL calls live at request time, holding the API key and a logged-in session cookie.

For

  • Live data and full design freedom at the same time — the only option that gets both.
  • A place to cache, precompute and shape data into an API that fits your league's rules exactly.
  • Could eventually serve a real mobile app or notifications.

Against

  • You now own credentials, a proxy, cache invalidation, and rate-limit compliance for your entire league funnelled through one IP — precisely the pattern MFL's per-IP throttle is built to catch, and the exemption in-page code enjoys is forfeited.
  • Revised, and now firmer. The first draft called this "leaning on the letter rather than the spirit." With MFL's terms in hand it reads worse than that: cross-domain JavaScript access is listed under forbidden uses, alongside "looking for loop holes or other ways to cheat or circumvent league rules." A proxy exists purely to defeat a restriction MFL states plainly.
  • Most to maintain, most to break, highest chance of a forced rewrite when MFL changes login or session handling.
  • Directly contradicts "stable year to year."

Verdict Not recommended — on stronger evidence than the first draft had. It buys design freedom at exactly the price you said you didn't want to pay, and does it against MFL's written terms.

TIER 5 · later, if you want one

Hybrid — Tier 2 for the league, a small public site for the front porch

The in-MFL app owns everything that needs authentication: cap sheets, contracts, commissioner tools, live views. A separate static site owns the read-only, no-auth material — league history, bylaws, records, hall of fame, championship charts.

For

  • Each half uses the mechanism it's actually suited to, with no compromises in either.
  • The public site can be genuinely beautiful and shareable without touching a credential.
  • League history is exactly the content that doesn't need to be fresh — the Tier 3 staleness problem evaporates.

Against

  • Two build targets and two deploys, even in one monorepo.
  • More concepts for a future commissioner to hold in their head.
  • Easy to start and never finish, leaving a half-built second site.

Verdict A good year-two move on top of Tier 2, not a starting point.

TIER 6 · due diligence

Leave MFL for a platform with native contracts

League Tycoon handles salary caps, multi-year extensions, rookie scales and franchise tags natively at about $12 per team per year, and imports MFL salary and contract data plus past seasons. Fantrax has native salary cap and a cleaner web UI, but a weak app.

For

  • The contract logic you hand-maintain becomes someone else's product feature. The annual JavaScript ritual ends permanently.
  • Modern, mobile-first UI is their problem, not yours — and it's the whole basis of their competition.
  • Import claims to carry salaries, contract years and up to 20 prior seasons across, so the history isn't necessarily lost.

Against

  • Your rules are idiosyncratic. Anything the platform doesn't model natively — your specific cap-penalty formula, your rookie salary curve, your RFA handling — becomes worse than today, because you lose the escape hatch of writing your own code.
  • MFL's openness is precisely why this repo works at all. A polished closed platform trades that away.
  • Migration risk mid-dynasty, and buy-in needed from every owner.
  • Betting a 25-year league on a newer company is a bigger bet than staying.

Verdict Worth an hour of looking so you know what you're choosing against. Not a recommendation — your custom rules are the reason to stay.

Independent of which option you pick

What to actually design

The technology question is separate from the information-architecture one. These apply either way.

Lead with one "My Team" view

Today the contract tab opens with every rostered player in the league, grouped by contract year. That's a reference document, not a landing page. The questions members actually arrive with are: how much cap space do I have, am I legal on roster count, who's expiring, and what does it cost me to cut this guy. Put those five numbers at the top, for the logged-in franchise — you already know who they are.

Cards on phones, table on desktop, one data source

A seven-column contract table is the right tool at 1200px and useless at 390px. Render the same player objects as stacked cards below a breakpoint. This single change does more for perceived quality than any restyling.

Make contract state legible, not numeric

"Years: 0" currently means restricted free agent, which you have to know to read. A badge — RFA, Expiring, Signed thru 2028 — carries it at a glance. Encode state in form and color, not just digits.

Advanced things stay possible, but behind a door

The cap penalty calculator, the rookie salary scale, the franchise-tag tables and the commissioner forms are all genuinely useful and none belong on first paint. Put them behind a Tools section. Progressive disclosure is how you get "common functions easy, advanced functions possible" without two separate sites.

Design the empty and slow states

Eight chained requests means members currently stare at a blank column. Render the shell immediately, fill sections as data lands, and say something when a fetch fails instead of silently rendering nothing.

So you're not rewriting this in 2029

The year-to-year stability checklist

Whatever you build, these are the rules that decide whether it survives unattended. Most of the current pain traces to breaking three of them — and the injuries bug traces to a fourth.

  • Derive year and league ID from document.location. Never hardcode a season.
  • Depend on exactly one MFL DOM hook — your own mount point. Delete the #tabcontent0 / #homepagecolumn1 reach-in, which currently works around eight duplicate IDs in MFL's own markup.
  • Use only documented export?TYPE= endpoints, on the right host — league-scoped calls to the league server, L-less calls (players, injuries) to api. The injuries bug is what forgetting this costs.
  • Validate every response's shape. Never treat HTTP 200 as success — that is exactly how a dead feature stays invisible for years.
  • Compute the post-deadline franchise and rookie baselines rather than pasting generated code. If a snapshot is genuinely needed, store it in MFL, not in the source file.
  • Pin exact dependency versions, and vendor them into the build so a CDN outage isn't a league outage.
  • Keep the paste fallback working — it is Tier 2's safety net, and the reconciliation shows it is faithful. (League file space is CSS-only as far as we could verify, so don't rely on it for JS.)
  • Write down the season rollover procedure in the repo. There isn't a README today, and the ritual lives only in your head.
  • Prefer boring, dependency-light code. This site is edited a few days a year by one person; cleverness costs more than it returns.
